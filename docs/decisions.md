# Design decisions

Why the model is the way it is. One row per decision, newest last.

| # | Date | Decision | Rationale |
| --- | --- | --- | --- |
| 1 | 2026-10-13 | Channels: the core covers public stores; private channels and AppGallery are foreseen as V13 options; Enterprise excluded | Each channel adds its own consoles and credentials; leaving them as a variant lets them be added without redoing the catalogue |
| 2 | 2026-10-13 | iOS extensions as targets (the main app and each extension) with their own App ID and profile | Each extension is a profile to renew; an app with push notifications usually has at least a notification service extension |
| 3 | 2026-10-13 | Generic internal approvals in the base, detailed in a regulatory-profile layer per sector and country | Keeps the base neutral and avoids repeating controls across clients in the same sector |
| 4 | 2026-10-13 | Custodian (A12) and signer (A13) kept separate; may be merged in an instance, with an alert | A small client cannot meet the segregation, but the model must be able to express it |
| 5 | 2026-10-13 | A new publication is modelled; updating an app under another account is a reference-only alternative flow (V11.b) | It is the general case; a transfer drags Team ID and key changes that deserve separate treatment |
| 6 | 2026-10-13 | Every data point with a deadline, limit or cost carries a source and a verification date | Store rules change every year |
| 7 | 2026-10-13 | Seven lanes by area (L1–L7) and V14 for who runs the technology | Business decides and owns, IT answers, the executor may be in-house or a third party; with that the diagram serves every client |
| 8 | 2026-10-14 | Estimated durations per phase and a "ready to publish" checklist in the base | They are the two questions business asks most: when, and what is missing |
| 9 | 2026-10-14 | Tracking by milestones (10) instead of by steps (45) | Ticking 45 steps per version is tedious and duplicates the checklist; steps remain reachable from each check |
| 10 | 2026-10-14 | Correction: Apple allows one certificate per distribution type per team, not "max 3" | The official page says so; the previous figure came from secondary sources |
| 11 | 2026-10-14 | Repository for the base model; Claude artifact for shared operations | Tracking real clients is internal information and must not sit in a public repository; the artifact already solves sharing and roles |
| 12 | 2026-10-14 | Repository in English, model content in Spanish, declared with `lang: "es"`; UI strings extracted to `generator/i18n/` | Open-source conventions for anyone contributing structure or code; the content is reviewed by Spanish-speaking business, security and legal teams and translating it without a domain reviewer would introduce errors and double the maintenance. The `lang` field and the i18n file leave the door open to other languages without touching the model |
| 13 | 2026-10-14 | Enum values in English (`ios`/`android`/`both`, `owner`/`app`/`version`/`cycle`, `high`/`medium`) with labels in the data or i18n file | Code compares against enums; labels are content. Mixing them would force Spanish literals into the code |
| 14 | 2026-10-22 | Financial features declaration (validation row 31) applies to every app published on Play, not only financial ones; noted on S12.7 | The official page moved (answer/13516546 → 13849271) and states that apps without financial features must also complete it |
| 15 | 2026-10-29 | Timeline from step dependencies: a phase waits for the earlier phases its steps depend on; dependencies on a later phase are read as overlap; two scenarios (all minimum, all maximum) instead of one probable date; optional `start_date` per instance | No new data to maintain: the step graph already says what waits for what. Summing every phase overstated the total (26–141 days vs 24–131) because the listing runs in parallel with signing and build. A single "probable" date would hide how wide the range is |
| 16 | 2026-10-29 | The plan moves from phases to the 25 diagram activities, with explicit `duration` and `after` in `diagram.json`; days are editable per client, activities can be marked done, and instances can add their own activities (`extra_activities`). Supersedes how decision 15 computed the timeline | Business plans and talks in diagram activities, not phases; deriving the order from step dependencies hid why an activity waited. A client-specific stage such as a pilot run must fit the plan without entering the neutral base |
| 17 | 2026-10-29 | Each client's generated output goes to `clients/<id>/dist/` instead of `dist/clients/<id>/` and `dist/diff-<id>.md` | With a private overlay linked into `clients/`, the output lands in the private repository next to the instance: one folder holds everything for the client and no manual copy goes stale. The base `.gitignore` shrinks to `clients/*` |
| 18 | 2026-10-30 | Activity 10 only generates keys; new activity 26 holds custody, handover and the credential inventory, after 11. S6.13 waits for S7.2. S11.3 waits for S8.4, and S11.4 carries the same rule as a note because it mixes tracks | Custody needs what 11 issues, so 10 could not finish before 11 started; fingerprints need the Firebase project to exist; no external tester should get a build without its security analysis. 26 is the next free ID: splitting 10 would break stable IDs |
| 19 | 2026-10-30 | Target platforms are a variant (V15), and each diagram activity gets `platform` and `joint`. With two platforms the plan runs one node per activity and platform, with joint activities as single nodes waiting for both. The 26 activities are not split | One state per activity hid that one store can move while the other is blocked, and a project could not target a single store. Splitting activities would duplicate most of the diagram; nodes reuse the same calculation and leave instances without platform data unchanged |
| 20 | 2026-10-30 | Activity 8 moves to L2 and only defines the identifiers; new activity 27 creates the app in the stores, after 9. S5.1 goes to A05 and A06, consulting A09 and validated by A07; S5.3 to A05 and S5.4 to A06. A14 keeps review and release | Identifiers are permanent and technical, and the consoles belong to IT. Creating the record is not publishing, so build and release stay separate. S5.3 needs the App ID from 9, so it could not sit in 8 |
| 21 | 2026-10-30 | Activities are renumbered 1–28 in flow order, with new activity 5 for creating the developer accounts (S2.1 and S2.4, run by A05 and A06, answered for by A03 and A04). Arrows move to an explicit `arrows` list in `diagram.json` | Numbers read as the order of the flow, and activities 26 and 27 broke that. No box showed account creation. Arrows computed from every dependency were unreadable. Rows 18 and 20 use the earlier numbers; row 23 replaces these numbers with keys. Old → new: 1–4 → 1–4; 5 → 6; 6 → 7; 7 → 8; 8 → 9; 9 → 10; 27 → 11; 10 → 12; 11 → 13; 26 → 14; 12 → 15; 13 → 16; 14 → 17; 16 → 18; 17 → 19; 15 → 20; 18 → 21; 19 → 22; 20 → 23; 21 → 24; 22–25 → 25–28 |
| 22 | 2026-10-30 | Activities 7 and 8 merge into "Invita usuarios y asigna roles" (L2), leaving 27 activities. S3.1 and S3.2 move to the account activity (5), S3.3–S3.5 stay as conditions of 7, and new step S1.7 gathers the registration data under activity 4 | Apple asks for its agreement after verification and before payment, and Google during sign-up, so they do not come after the account is verified. Without them 7 only invited the Admins. Nothing gathered the registration data before creating the account. Old (row 21) → new: 1–7 → 1–7; 8 → 7; 9–28 → 8–27 |
| 23 | 2026-10-30 | Activities get a stable `key`; the number shown is computed from the position. `after`, `arrows` and instances use keys, and UI strings use `{act:<key>}` | The number was both an identity and a position, so adding an activity meant renumbering. Instances are private and cannot be migrated from this repository, and a renumbered base would have moved their state to the wrong activity without any error. Incompatible with 1.3.0. Number in 1.3.0 → key: 1 decide-owner; 2 approve-stores; 3 create-identities; 4 gather-registration-data; 5 verify-entity; 6 and 7 assign-access; 8 define-identifiers and create-store-app; 9 register-app-ids; 10 generate-signing-keys and hand-over-credentials; 11 issue-certificates; 12 configure-services; 13 build-and-sign; 14 analyze-binary; 15 upload-and-test; 16 prepare-listing; 17 declare-and-approve; 18 security-approval; 19 go-no-go; 20 store-review; 21 release; 22 monitor; 23 analyze-crashes; 24 rotate-credentials; 25 handle-incidents. create-developer-accounts is new |
| 24 | 2026-10-30 | The plan has one date per activity instead of a fast and a slow scenario. `duration.days` is the midpoint of the former range, instances set `days` and `end`, and the roadmap shows what was postponed. Incompatible: `validate.py` rejects `min` and `max` in instances | Two calendars do not work for following a project: people need one date, and to see what moved when it is postponed |
| 25 | 2026-11-03 | Each activity lists its steps in `diagram.json`, and every step belongs to exactly one activity | The link between activities and steps lived only in each client's documents, written by hand, so it drifted and could not be reused. With it, the page shows the steps of an activity for each platform |
| 26 | 2026-11-03 | Milestones are activities marked with `milestone` (name, and type achievement or decision) instead of the end of each stage, and the roadmap opens with a summary: status, next milestone, publication and open blockers | Stage ends had no name and did not answer what business asks: when the account, the app, the build, each approval and the publication will be ready |
| 27 | 2026-11-03 | The roadmap opens with summary, open decisions and milestones, and keeps progress, areas, schedule and lists under a detail section. Instances add `open_decisions` and `baseline` | Decisions were what held the plan back but lived only in documents, and a committee needs one screen. The baseline turns "the date changed" into a deviation in days |
| 28 | 2026-11-03 | Every activity opens a sheet. Client activities may list `tasks` and `refs` (related model steps, which keep belonging to their own activity). What repeats across clients moves to the model or to a regulatory profile | Client milestones and activities had no detail, and copying the same activity into each client would drift |
| 29 | 2026-11-03 | The plan tests run in a browser on `clients/example` with a fixed clock, inside `check_page.py`, and are required on every pull request. Locally they are optional and can use the installed Chrome or Edge | The forecast, the platforms and the CSV had no automated check. CI machines can download a browser; some corporate machines cannot, so nothing local depends on it. Pure unit tests with `node --test` wait until the plan engine leaves `page_logic.js` |
| 30 | 2026-11-03 | The baseline stores the committed start and end of each activity, in one form, and the schedule draws it as a thin bar under each activity | The start was deduced from the current duration, so changing a duration after the approval moved the reference and the expected progress without notice. One strict form lets `validate.py` reject partial or inverted entries |
| 31 | 2026-11-03 | Slack goes into the CSV and, in the schedule, behind a button that shows and hides it, off by default | It matters for analysis, not for the daily status; always visible, it would crowd the view shown to committees |
| 32 | 2026-11-03 | Each postponement carries a reason: one of six neutral categories and an optional note, next to the end it explains | Without a reason the roadmap could count postponements but not explain them. Categories can be counted across activities and clients; free text alone cannot |
| 33 | 2026-11-03 | No weekly snapshots of the plan | A publication is a project of a few months with a clear end. Baseline against current dates, postponements with their reason, open decisions and the dated CSV already answer what moved and why. A weekly manual step tends to be abandoned and leaves a misleading chart. Revisit for a long programme or a portfolio of apps |
| 34 | 2026-11-03 | A client's plan lives only in its `instance.json`. The page edits it and downloads the whole updated file, adding a dated entry to `plan_log` with one line per change; it records what and when, not who | One person updates the plan and presents it, and client data may not leave the client's storage, so a shared database (the Claude artifact) or a hosted repository is not an option. Downloading the whole file removes the manual copy of fragments that lost changes, and the log travels with the file |
| 35 | 2026-11-03 | Risks are a light list per instance: severity high or medium, owner, mitigation, affected activities and status. No probability and impact score and no catalogue in the base model | Half of what was written as risks was already covered by open decisions, blockers and the critical path; the rest needs to be seen before it turns into a delay, with someone acting on it. A score adds fields without changing the action; a catalogue needs a source and a date for every figure. Add either if a risk area asks for it |
| 36 | 2026-11-03 | The committee view of the roadmap shows open decisions and high risks as one line each, in a block "Para decidir y vigilar"; the full tables move to the detail section | Two wide tables before the milestones made the view heavy. A committee needs what it has to decide and what to watch; days open, mitigations and medium risks are for whoever manages the plan |
| 37 | 2026-11-03 | S1.4, the Apple Account of the holder, belongs to activity 5 (developer accounts) instead of activity 3 | The Apple Account is created to enrol, and in organisations that restrict access to Apple it can only be created when that access is granted, together with the enrolment. S1.5 stays in activity 3: the Google Account usually exists before and does not depend on Play Console |
| 38 | 2026-11-03 | An instance may move a step to another activity of the model with `step_moves` | Where a client does a step depends on its own policies; changing the model for one client would impose it on all, and leaving the sheet as it is shows the step where it is not done |
| 39 | 2026-11-03 | An instance may skip the conditional steps that do not apply to it with `step_skips`, each with its reason. Only steps marked conditional in the model can be skipped | A sheet that lists steps a client will never do (charging, EU trader status) misleads whoever follows it. Restricting it to conditional steps keeps the model the reference: a client cannot drop a step the publication needs |
| 40 | 2026-11-03 | Instances may keep `notes` per activity, shown on the activity sheet | What a client must know to do an activity of the model lived only in its working documents, which the page does not show. Notes sit outside `plan` because the plan merges page edits, and a note there would keep an old copy |
| 41 | 2026-11-04 | S5.2 names the targets (the main app and each extension) instead of the codes T01–T06; row 2 and `validation.md` drop T01–T07 | The codes were never defined anywhere, so a reader of the sheet could not tell what T03 was. Naming the kinds of target, with an example such as the notification service extension, says what to register |
| 42 | 2026-11-04 | A step that exists only with one option of a variant declares `applies_if`; S5.5 applies only with V11 b. S18.5 keeps V11 without it, because an app may be transferred later whatever its origin | `variants` said that a step changes with a variant, not that it disappears with another option, so a client that chose a new app still saw the transfer step. Declaring it in the model saves every client from repeating it in its instance |
| 43 | 2026-11-04 | Durations are working days (Monday to Friday by default) and each instance declares its holidays in `calendar`. The model durations were converted with ceil(days × 5/7). Activities that run every day (entity verification, store review) are marked `"calendar": "calendar"` and kept as they were | The plan counted weekends and holidays as work, so a five-day task started on Monday ended on Saturday. Converting keeps the effort and lets weekends and holidays stretch it. Stores and pilot windows do not stop on the team's days off, so they stay in calendar days. Holidays are national, so they belong to the instance, with their source |
| 44 | 2026-11-04 | The start of an activity can be set by hand (`plan.<key>.start`), never before its predecessors end. It moves the activity without changing its duration and counts as postponed, with its reason. "Aplazada" counts only what an activity's own start or end moved it. The list and the CSV show the duration | An activity that began days after the previous one could only be recorded by extending its end, which said it took longer than it did. A free start would break the order of the plan, so it is bounded by the predecessors. Counting inherited moves as "aplazada" blamed an activity for another one's delay |
| 45 | 2026-11-04 | The milestone of activity 23 is "Despliegue completo"; the publication date in the summary is the day the app becomes visible, which is the end of the store review | Since 5.0.0 the summary dates publication at the start of the release, so a milestone called "App publicada" at its end showed a different date for the same event |

## Decisions still open

- Whether the regulatory profile is modelled as a `profiles/` folder with the same format as a partial instance.
- Whether P07, P09 and P24 are removed from platforms (they are tools, not platforms of the process) and whether V8 and V12 become step notes.
- Contingency plan: what happens if a store rejects for lack of a financial licence, if the account is suspended, or if the Account Holder leaves the company without transferring the role.
- Bilingual model content (`locales/<lang>/`) if a non-Spanish-speaking client appears.
