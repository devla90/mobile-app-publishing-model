# Deployment

## Static site (this repository)

`dist/` is a static site. Options:

- **GitHub Pages (optional).** Not enabled in this repository; see [GitHub Pages (optional)](#github-pages-optional).
- **Netlify or Cloudflare Pages.** Publish from a private repository and allow password protection. Build command: `python3 generator/build.py --no-png`. Publish directory: `dist`.
- **Local.** Open `dist/index.html` in a browser.

The static page keeps clients, versions and dates only in the browser of whoever opens it (`localStorage`, keys prefixed `mapm-`). There is no shared state and no roles.

## GitHub Pages (optional)

The repository does not publish anything by itself. To publish `dist/` from your clone:

1. `cp docs/github-pages/build.yml .github/workflows/build.yml` and commit it.
2. On GitHub: Settings → Pages → Source: *GitHub Actions*.

The workflow validates, builds with PNG and deploys on every push to `main` that touches `model/`, `clients/` or `generator/`. On the free plan, Pages only works for public repositories.

## Claude artifact (shared operations)

For the team to tick milestones and see the same state, the same page is published as a Claude artifact with the `db` and `user` capabilities. There:

- Clients and versions are stored in the artifact database, shared among those with access.
- Roles are the artifact's: Viewer reads; Contributor and above tick milestones and edit the instance.
- Claude can read or update the tracking from a conversation.

To regenerate the artifact after changing the model:

1. `python3 generator/build.py --no-png`.
2. Take `dist/index.html`. Remove `<!doctype>`, `<html>`, `<head>` and `<body>` wrappers (the artifact adds them) and the line `window.claude={use:async()=>null};`.
3. Publish with `capabilities: {db: {}, user: {}}`. `generator/templates/page_logic.js` already contains the `db` logic with local fallback.

## Branch protection

Protection is configured by the repository owner on GitHub, not by files in the repository. On the free plan, rulesets only work on public repositories (private ones need GitHub Pro). Recommended setup:

1. Settings → Rules → Rulesets → *New branch ruleset*. Name `main`, enforcement *Active*, target *Default branch*. Enable:
   - *Restrict deletions* and *Block force pushes*.
   - *Require a pull request before merging*, 1 approval, dismiss stale approvals on new commits.
   - *Require status checks to pass*: `validate` (from `.github/workflows/validate.yml`, which runs `validate.py` and `build.py --no-png` on every pull request).
   - If you work alone, add *Repository admin* to the bypass list with mode *For pull requests only*: you can merge your own pull requests, but not push to `main` directly.
2. *New tag ruleset*. Name `releases`, enforcement *Active*, target pattern `v*`. Enable *Restrict updates*, *Restrict deletions* and *Block force pushes*, so a published version cannot be moved.

Releases are tagged on `main` with semantic versions (`v1.0.0`) and described in `CHANGELOG.md`.

## Private client instances

Real instances hold internal information and never go into this repository. Only `clients/example/` (instance and output) is versioned; `.gitignore` excludes every other `clients/<id>/`, including its generated `dist/`.

Keep each real client in its own private repository (an overlay), next to the base:

```
app-stores/
  mobile-app-publishing-model/   this repository (public or shareable)
  <client>-private/              private repository
    clients/<id>/instance.json   plus the client's working documents
    clients/<id>/dist/           generated by build.py: page, diagram, diff
```

Link it into the base and build:

```bash
ln -s ../../<client>-private/clients/<id> clients/<id>
python3 generator/validate.py && python3 generator/build.py --no-png
```

Edits made through the link land in the private repository; commit them there. The build writes the client's output into the same folder, `clients/<id>/dist/` (`index.html`, `swimlanes.svg`, `swimlanes-<id>.drawio`, `swimlanes.png`, `diff.md`), so it also lands in the private repository: one folder holds everything for the client and can be shared as is.

`generator/validate.py` fails if any file under `clients/` other than `clients/example/` is in the git index (and if anything is left under the old `dist/clients/` or `dist/diff-*.md`), so a forced `git add -f` is caught before the commit and in CI. Before pushing to a public remote, `git status --ignored` should list each real instance as ignored (`!!`).

Before pushing the base, confirm nothing leaked:

```bash
git check-ignore -v clients/<id>   # must match a rule
git status --short                 # no line with <id>
```

CI (`validate.yml` and, if enabled, the optional Pages workflow) only sees committed files, so it never builds or publishes a real instance.

## Diagram

`dist/swimlanes.svg` can be edited in PowerPoint, Visio or Figma. `swimlanes.png` is 2x for presentations. Per client, in `clients/<id>/dist/`.

`dist/swimlanes.drawio` is the same diagram for draw.io (desktop or app.diagrams.net). Lanes are containers, activities keep their number, lane, stage and phases as data (*Edit Data*), and arrows are connected to the activities, so they follow when a box is moved. It is generated with the SVG from the same layout, so both always match. Per client it is named `clients/<id>/dist/swimlanes-<id>.drawio`, so several clients can be opened in draw.io without mixing them up.

The `.drawio` is output, not source: every build overwrites it. Change the diagram in `model/diagram.json`; edit the `.drawio` by hand only in a copy outside any `dist/`.

## Other UI languages

`python3 generator/build.py --lang <code>` uses `generator/i18n/<code>.json`. To publish two languages, build twice into different folders (the generator writes to `dist/`; copy or rename between builds).
